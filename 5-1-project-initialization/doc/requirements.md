# 智能知识问答系统 需求文档

> 版本：v1.0　｜　状态：需求已澄清，待评审
>
> 本文档只回答"做什么"，不涉及"怎么做"。所有功能均附验收条件。

## 一、用户角色与用户故事

系统面向两类角色：

**普通员工（提问者）**：公司内部员工，需要从散落的内部文档里快速找到答案，不想逐个翻文件。

- 作为员工，我想上传自己的文档并按主题分库管理，这样不同领域的资料不会混在一起。
- 作为员工，我想用自然语言直接提问，这样不必猜关键词。
- 作为员工，我想在一次对话里连续追问，这样不用每次都把背景重复一遍。
- 作为员工，我想在答案里看清系统是不是真的在文档里找到了依据，这样我能判断答案可不可信。
- 作为员工，我想回顾自己过去问过的问题，这样能快速找回之前查到的信息。

**管理员**：负责维护知识库内容、掌握系统使用情况。

- 作为管理员，我想统一管理知识库和文档，这样能保证内容的准确和时效。
- 作为管理员，我想查看用户的问答记录，这样能了解大家在问什么、系统答得怎么样。

## 二、功能列表与验收条件

### 1. 多知识库管理

用户可创建多个知识库，并在提问前选择当前使用哪一个；不同知识库的文档相互隔离。

- 用户能创建、命名、切换、删除知识库。
- 提问时明确归属到某一个知识库，问答只在该库范围内进行，不跨库检索。
- 删除知识库时给出二次确认，避免误删。

### 2. 文档上传与解析

用户上传文字版文档，系统自动解析入库；解析失败时明确告知原因。

- 支持上传含可提取文字的 PDF、Word、TXT 文档。
- 上传扫描件、图片型 PDF 等无可提取文字的文档时，在上传环节即拦截，并明确提示"该文档无可提取文字，暂不支持"，不静默失败、不入库空内容。
- 解析成功后，文档在对应知识库中可见、可被检索。
- 单份文档解析失败（如文件损坏、格式不符）时，显示具体失败原因，不影响其他文档。

### 3. 智能问答

用户提问，系统基于所选知识库的内容作答；检索不到时如实说明。

- 回答内容以所选知识库的文档为依据。
- 当知识库中检索不到相关内容时，系统先如实说明"文档中未直接找到相关内容"，再基于常识尝试作答，并在回答中标明这部分属于推测，不伪装成文档依据。
- 回答采用流式输出：提问后逐字实时输出，首字节延迟不超过 3 秒。

### 4. 多轮对话

同一次会话内支持连续追问，系统理解指代。

- 在当前会话内，系统能结合前几轮问答理解"它""这个"等指代，无需用户重复背景。
- 上下文仅在当前会话内有效；用户刷新页面或新开会话后，上下文清空、重新开始。

### 5. 历史记录

保存用户提问历史，供回顾。

- 用户能查看自己过去的提问及对应回答。
- 历史记录仅用于回顾展示，不作为后续新提问的上下文（与"多轮对话的上下文"相互独立）。

### 6. 管理后台

管理员管理知识库与文档，并可查看用户问答记录。

- 管理员能对知识库和文档进行增删改查管理。
- 管理员可查看用户的完整问答记录，包括具体问题与系统回答内容。
- 上线时须明确告知用户"问答记录对管理员可见"，避免用户误以为是私密空间（详见风险点）。

## 三、边界声明（本期不做）

- **不做答案来源引用**：回答不标注出自哪份文档、哪个段落，用户无法在答案上点击核对原文。（注意：这与"检索不到时标明推测"存在张力，见风险点）
- **不支持扫描件 / 图片型文档**：无可提取文字的文档一律在上传环节拦截，本期不做图片文字识别。
- **不做跨知识库检索**：一次提问只在单个知识库内进行。
- **上下文不跨会话延续**：不记忆历史会话的对话上下文。
- **暂不面向外部客户**：本期只面向公司内部员工，对外开放看后续运营节奏，不在本期范围。

## 四、风险点

- **隐私与审计的张力**：管理员可查看全部问答内容，与"保护用户隐私"的初衷存在冲突。员工可能在提问中涉及个人或敏感业务信息。需在上线前明确告知用户记录可见，并由后续阶段评估是否需要脱敏、分级访问等配套措施。
- **可信度缺少可核对的抓手**：本期不做来源引用，用户无法逐句核对答案出处。"文档依据"与"系统推测"的区分只能靠回答文字措辞传达，一旦措辞不清，用户可能把推测当成文档结论。后续需评估是否补上来源标注。
- **"尽快上线"缺少明确时间与验收门槛**：原始需求只提"争取尽快上线"，未定上线时间和第一版的整体验收标准。首版功能范围已在本文档明确（上述六项全部纳入），但整体上线时间点仍需产品与开发共同拍定。
- **"准确"缺少统一评判标准**：问答"准确"目前只能靠人工主观判断，尚无一套统一的评测方法来衡量答对率。后续需要建立一批标准问答样例来评估质量，这属于开发阶段要补的评测设计。
